# CLAUDE.md

Guidance for working in this repo — read this before making changes, and keep it
accurate as conventions change.

## What this is

**PowerPlatformer** — a 2D browser platformer about chaining temporary power-ups
through a hand-built level. Built with Vite + TypeScript + raw HTML5 Canvas 2D (no
game framework). Controls are **mouse/touch only, no keyboard** — this was an
explicit, repeated design decision; don't reintroduce keyboard input.

Theme: "Farting Power" — a stamina resource that fuels every action (movement,
jumping, attacking, flying), visualized as fart-propulsion effects (puff
particles from the player's butt, a jet while flying, comic "BRAAP!" text). The
player sprite is a hand-drawn stick figure (see "Sprite pipeline" below), not
procedural art. Everything else uses a **notebook doodle** style: lined paper,
wobbly pencil outlines with hatching, handwritten fonts — drawn procedurally in
`src/doodle.ts` to match the hand-drawn hero.

Deployed via GitHub Pages at `https://aloumvrios.github.io/PowerPlatformer/`,
auto-deployed by `.github/workflows/deploy-pages.yml` on every push to `main`
(`npm run build` → upload `dist/` → Pages). There is no separate staging step —
pushing to `main` ships.

## Stack & file layout

- `src/main.ts` — entry point. Wires up `fitCanvas()` (see "Canvas scaling"
  below), loads the bundled fonts, unlocks audio on the first pointer event,
  starts `Game`. In dev builds it also exposes the game as `window.__game` for
  Playwright/console poking (stripped from production).
- `src/game.ts` — the entire game: the `Game` class, its state machine, the
  `update(dt)`/`render()` loop, all physics/economy constants, particles and
  "juice", sprite selection, and the canvas-drawn HUD, title, pause and end
  screens. This file is intentionally a monolith; it has grown large through
  iterative feature work rather than being split into systems, and that's fine
  for this project's size — don't split it up preemptively.
- `src/doodle.ts` — pure drawing helpers for the notebook-doodle art: seeded
  wobbly lines/rects/circles, hatching, paper background + parallax, platforms,
  spikes, toilet, checkpoint flag, pickup icons, beans, enemy, HUD icons,
  buttons, hand-lettered text. No game state.
- `src/audio.ts` — WebAudio sound effects (see "Sound" below).
- `src/view.ts` — `VIEW_W`/`VIEW_H` (960×540), the logical coordinate space.
- `src/input.ts` — translates raw Pointer Events into the game's four discrete
  input primitives (click target, jump target, attack direction, fly target). See
  "Controls model" below. Game logic never touches `PointerEvent` directly.
- `src/level.ts` — the hand-built levels (`level1`, a left-to-right run, and
  `level2`, a taller winding stage built from the user's pen sketch — its
  coordinates are the sketch photo's pixels, scaled by `sk()`) and `STAGES`,
  the ordered list of playable stages (`{ id, name, level }`). A level has
  one-way `platforms`, solid `solids`, `hazards` (spikes; `dir` says which way
  they point), `enemies` (urchins or crawlers, patrolling along x, or y with
  `axis: "y"`), pickups, checkpoints, `stalls` (see "Stalls" below),
  pencilled-on hints, background `decor`, and the goal (drawn as a toilet). No level editor or loader — edit the array literals
  directly. Winning a stage moves on to the next (back to the first after the
  last). A stage's `id` keys its presets and saved best times, so keep it
  stable once shipped.
- `src/nav.ts` — distance to the toilet *along the level* (a distance field
  over the open space, spread from the goal), so progress through a winding
  level is measured along its route. Drives the Holding Power ramp and the
  bots' sense of progress. Solids block it; one-way platforms don't.
- `src/sprites.ts` — imports every player sprite PNG, exposes `sprites: Record<SpriteName, HTMLImageElement>` and the `JUMP_SEQUENCE` animation order.
- `src/tuning.ts` — the `Tuning` interface (every Farting Power / Holding Power
  rate and pickup value), `DEFAULT_TUNING`, and `presetFor(stageId, difficulty)`:
  `DEFAULT_TUNING` overlaid with that stage's entry in
  `src/difficulty-presets.json`. That JSON is **generated by the balancing
  simulator** — re-tune rather than hand-editing (the PR check will catch a
  hand edit that lands off target).
- `src/sim/` — the headless balancing simulator: bot personas play the real game
  logic to gather player metrics and tune the difficulty presets. Node-only (not
  part of the bundle); see `src/sim/README.md`. `scripts/sim.mjs` is its launcher.
- `docs/difficulty-tuning.md` / `docs/difficulty-baseline.json` — the report and
  headline numbers from the last `tune` run; the baseline is the "before" in
  the PR check.
- `.github/workflows/difficulty-check.yml` — on PRs that touch levels, physics,
  economy or the sim: simulates every stage × difficulty, comments the numbers
  and **fails if a preset is off target or a stage isn't tuned** (meant to be a
  required check on `main`). `.github/workflows/difficulty-tune.yml` — manual
  "Run workflow" that re-tunes and opens a PR with the results.
- `src/types.ts` — shared interfaces (`Rect`, `Level`, `PowerUp`, `Enemy`, etc.).
- `src/style.css` — the page is just the canvas on a "desk" background; there is
  no HTML UI — HUD, menus and buttons are all drawn on the canvas.
- `src/assets/sfx/` — optional real recordings that override synth sounds (see
  its README).
- `src/assets/player/*.png` — hand-drawn sprite frames (see pipeline below).

## Controls model (`src/input.ts`)

Everything is driven by the Pointer Events API (`pointerdown`/`pointermove`/
`pointerup`/`pointercancel`), which unifies mouse and touch. A press is
disambiguated into exactly one of:

- **Single click/tap** → a short aimed "weak launch" toward the click point
  (`consumeClickTarget()`), direction computed relative to the player's on-screen
  position, not a fixed screen side.
- **Double-click/tap** (within `DOUBLE_CLICK_MS` and `DOUBLE_MAX_DX`) → a full-
  strength aimed launch/jump (`consumeJump()`).
- **Press and hold** past `HOLD_THRESHOLD_MS` without drifting past
  `HOLD_STATIONARY_PX` → flight, read continuously via `getFlyTarget()` (not
  consumed — it's live state for as long as the pointer is held).
- **Right-click, or a touch swipe** (`SWIPE_MIN_DX`/`SWIPE_MAX_DY`/`SWIPE_MAX_MS`)
  → an attack, resolved to a direction (`1 | -1`) via `consumeAttack(playerScreenX)`.
  A swipe already carries its own direction; a right-click's direction is resolved
  against the player's current screen x (right-click left of the player attacks
  left, right of the player attacks right) — `input.ts` doesn't know the player's
  position, so that resolution happens in `game.ts` at call time, not at click
  time.

All positions `input.ts` hands back are in the **logical 960×540 space**
(`canvasLocalPoint()`, using `VIEW_W`/`VIEW_H` — not CSS pixels, and not
`canvas.width`, which is the HiDPI backing-store size and varies per device), so
`game.ts` can compare them directly against `player.x`/`player.y` without any
further conversion.

**On-canvas buttons** (pause/mute/fullscreen): `game.ts` registers their rects
every frame via `setUiButtons()`. A press that *starts* on a button never becomes
a game action; the button's `onPress` fires synchronously on release, inside the
pointer event, because fullscreen and audio unlock need a real user gesture (a
callback deferred to the next `requestAnimationFrame` wouldn't qualify). Press
and release are matched by the button's **`id`**, not object identity — the rects
are fresh objects every frame, so an identity check silently drops any press
longer than one frame (which, for a real person, is nearly all of them).

`getPressIndicator()` exposes the press currently being decided (0→1 over
`HOLD_THRESHOLD_MS`) so `game.ts` can draw a filling ring — that's what makes
"hold to fly" discoverable.

## Canvas scaling — a gotcha, read before touching layout

The game has a **fixed logical resolution** (960×540, `VIEW_W`/`VIEW_H`) but the
canvas is **scaled to fit the real viewport** by `main.ts`'s `fitCanvas()`, which
sets `canvas.style.width/height` in px on load and on `resize`/
`orientationchange`, preserving the 16:9 aspect ratio. `style.css` centers the
(possibly letterboxed) canvas via flexbox on `body`.

`fitCanvas()` also sets the **backing store** (`canvas.width/height`) to that CSS
size × `devicePixelRatio` (capped at 2) so line art is crisp; `render()` starts
with `ctx.setTransform(canvas.width / VIEW_W, …)` and draws everything in logical
units. So never use `canvas.width` as "the viewport width" in game logic — use
`VIEW_W`.

**This matters because `input.ts`'s `canvasLocalPoint()` relies on
`getBoundingClientRect()` exactly matching what's actually drawn.** If you ever
change canvas sizing to something like `width: 100vw; height: 100vh; object-fit:
contain;`, the element's layout box (what `getBoundingClientRect()` returns) and
the actual rendered/letterboxed content area diverge — `object-fit` scales the
*painted* content without shrinking the box, so click/tap coordinates go wrong in
exactly the regions that matter most (near screen edges). Keep canvas sizing as
explicit JS-computed pixel dimensions, not CSS-only `object-fit`.

This also used to break mobile progression: before `fitCanvas()` existed, the
canvas rendered at its raw 960×540 size unscaled, so on a narrow phone screen it
overflowed and got clipped by `overflow: hidden` on `html, body` — including
clipping off the player's spawn point — while the camera (which scrolls against
the full 960px-wide internal viewport in `game.ts`'s `update()`) only caught up
long after the player had already walked past what was visible. It read as "the
camera doesn't follow" / "the player gets stuck at the edge of the screen".

## Difficulty

Presets are **per stage**. An Easy / Medium / Hard picker (on-canvas text
buttons via the same `setUiButtons()` path as pause/mute; a press on one never
starts or resumes the run) sits under the title card and under the pause,
game-over and win cards. Changing it while paused restarts the stage (still
paused), since the meters would otherwise mix two sets of values; on the end
cards the next run just uses the new difficulty. The choice and the best time *per stage and difficulty* are saved in
`localStorage`. Difficulty only swaps the `Tuning` object; physics, level and
lives are the same in every mode.

## Headless mode (used by the simulator)

`new Game(null, { headless: true, input })` has no canvas, listeners, sound or
saved best times; it only advances when `tick(dt)` is called. `loop()` is just
`tick()` + draw. All input goes through `this.input` (an `InputSource`,
`pointerInput` by default) — **don't call `input.ts`'s consume functions
directly from game logic**, or bots stop being able to play. The sim reads
state through the public getters in the "simulator API" block and
`runSummary` (which includes the per-run `RunStats`). Physics constants the
bots' forward model needs are exported from `game.ts`; if you change how
movement works in `update()`/`moveAndCollide()`, mirror it in
`src/sim/forward.ts`.

## Camera

Follows the player on both axes with smoothing, clamped to the level. x leads
in the facing direction; y keeps the player in the lower part of the view. A
level only scrolls vertically if it's taller than `VIEW_H`. Anything that
converts between screen and level coordinates (click targets, ripples, the
bots' taps) must use both `cameraX` and `cameraY`. The paper background's
doodles (sun, clouds, hills) sit at the bottom of a tall level and slide out of
view by parallax as the camera climbs.

## Game states (`src/game.ts`)

`status` is one of `title → playing ⇄ paused`, `playing → dying → playing |
gameover`, `playing → winning → won`; `won`/`gameover` restart on tap. Menu-ish
states *always* drain input (`consumeAnyAction()`) and only act on it after a
short lock-out, so a tap made during the lock-out is dropped rather than queued.
`playing` also drains input for its first `INPUT_GRACE_SEC`, so the tap that
started the run (or the second half of a double-tap) doesn't launch the player.
Leaving the tab/window auto-pauses.

Dying: a hit without a shield costs a life and plays a short tumble (or nothing,
for falls), then respawns at the last reached checkpoint with a blinking
invulnerability window. Power-ups are restored on respawn; beans, killed enemies
and checkpoints keep their progress. A shield hit instead knocks back and grants
the same invulnerability window (before that existed, the shield broke and the
next frame's contact killed you anyway).

## The `Game.update(dt)` loop (`src/game.ts`)

Order of operations matters and has bitten this project before:

1. Decay active timed power-ups.
2. **Regenerate Farting Power first**, before any action this frame spends it.
   This ordering is deliberate — see "Farting Power" below. Holding Power
   drains here too.
3. Resolve flight (`getFlyTarget()`), else resolve buffered weak-launch/jump
   requests, else apply gravity.
4. Attack cooldown/flash decay, `consumeAttack()`.
5. Integrate position, clamp to level bounds, collide (`moveAndCollide()`):
   x then y against solids, then one-way platforms.
6. Hazards, enemies, pickups/beans/bananas/checkpoints, goal, Holding Power
   "accident" (after pickups and the goal, so a last-second banana or reaching
   the toilet that frame still saves you), fall-death.
7. Track `bestProgress`, idle toots, low-Holding-Power rumbles, squash/stretch easing, smoothed look-ahead camera, flight-jet
   sound.

**Two kinds of terrain.** **Solids** block from every side (walls, floors,
ceilings — a jump or flight bonks off them); movement is resolved one axis at a
time, x first, then y. **Platforms are one-way** (including stage 1's ground):
you rise through them from below or the side and only land from above. Landing compares against *last
frame's* feet position, so fast falls can't tunnel through 20px platforms. On
the ground, leftover horizontal speed bleeds off via `GROUND_FRICTION` (a short
skid shown with the `run1`/`run2` frames) instead of stopping dead.

### Farting Power (the stamina economy)

A 0–100 meter that regenerates passively (`tuning.fartingRegenPerSec`) and is spent by
every action. **Design rule: depletion is a soft penalty everywhere except
flying** — weak launches, jumps and attacks just get weaker (`DEPLETED_*_MULT`)
when it hits 0, they never lock you out. Flying is the one hard stop: running out
mid-flight forces an immediate landing, even if the pointer is still held.

Getting that hard stop to actually trigger required two fixes, both still load-
bearing:

- **Regen must run before costs are applied in the same frame's `update()`**, not
  after. Otherwise a cost that clamps the meter to exactly 0 gets topped back up
  by that same frame's regen before the *next* frame's depletion check ever sees
  the 0 — the meter visibly plateaus just above 0 and forced-landing never fires.
- **`flightExhausted` is sticky**, not a plain `fartingPower <= 0` check. It's set
  `true` once depletion happens mid-flight, and only cleared when the pointer is
  released (`getFlyTarget() === null`). A non-sticky check would let a single
  frame's regen tick re-engage flight immediately after exhaustion, since regen
  runs before the check each frame.

If you touch this again and the hard-stop regresses, it's almost certainly one of
these two orderings.

### Holding Power (the stage timer)

A second 0–100 meter: how much longer the hero can hold it in. It drains on its
own at `tuning.holdingDrainPerSec × holdingDrainMult()`, where the multiplier ramps
(eased in, `progress²`) from 1 up to `1 + tuning.holdingProgressExtra` as the player
nears the toilet. Progress is `bestProgress` — the furthest the player has got
this life, measured along the route by `nav.ts` (0 at the start, 1 at the
toilet) — **not** the current position, so walking back doesn't buy time;
it's reset to the spawn point on each (re)spawn.

The trade-off with Farting Power: anything that refuels gas drains Holding Power
(`tuning.holdingBeanCost`, `tuning.holdingBeansoupCost`), while bananas
(`level.bananas`, constipating) refill it (`tuning.holdingBanana`) at the cost of
a little gas. Bananas
stay eaten after a respawn, like beans. `tuning.beanShare` (0–1) thins out a
stage's beans per difficulty (`beanPresent()` in `tuning.ts` spreads the
removals evenly): left-out beans start the run marked collected, so nothing
else needs to know, and the HUD counts only the beans actually placed.

Hitting 0 is an "accident" — `die("accident")`, which costs a life like any
other death (`dyingCause` is `"hit" | "fall" | "accident"`). Reaching a
checkpoint saves the current Holding Power; a respawn restores that, floored at
`tuning.holdingRespawnMin` so one accident can't snowball into a death spiral. Below
`HOLDING_LOW` the stomach rumbles (`updateRumble()`), the screen shakes and the
hero trembles.

### Stalls

Spots that hold the player up for a few seconds while Holding Power keeps
draining (`level.stalls`, `Stall` in `types.ts`). So far: `"npc"`, the
pants-insurance salesperson. `checkStalls()` starts one when the player is
**standing on the ground** inside its rect — jumping or flying past avoids it,
at a gas cost. While stalled, the movement part of `update()` is skipped (the
player is frozen; hazards, enemies and the meters still run), and taps or
double-taps go to `updateStall()` instead of launching: each shaves
`STALL_TAP_SEC` off, but a stall always lasts at least `STALL_MIN_SHARE` of its
full length (`tuning.stallNpcSec`, per difficulty). Each stall happens once per
run (`done` survives a respawn, like checkpoints; a death mid-stall leaves it
to trigger again). `renderStall()` draws the speech bubble and the "tap to
hurry" ring. The bots model being caught (`"stall"` outcome in
`src/sim/forward.ts`), weigh its time cost, and mash taps at their persona's
`tapRate`. Adding a new kind: extend `Stall["kind"]`, `stallSeconds()`, the
render/finish branches, a `Tuning` duration (and its `PARAM_BOUNDS`), and the
bots' cost estimate in `agent.ts`.

### Sprite selection

`currentSpriteName()` is a priority chain (dying/winning poses > attack flash >
powerup flash > flying > weak-launch hop > fly-power-up jump-flap > jump sequence
by air time > skid (run frames) > standing). Squash/stretch, lean and breathing
are applied as transforms around the sprite's bottom-centre in `renderPlayer()`.
`renderPlayerSprite()` flips the sprite horizontally via
`ctx.scale(-1, 1)` when `player.facing === -1` — this is also what makes the
attack-direction fix visible (facing is set from the resolved attack direction,
not just movement).

## Art (`src/doodle.ts`)

Wobble is **seeded**, not random per frame, so shapes hold still — except for a
deliberate "line boil": `setBoil()` cycles the seed through 3 variations ~7×/s,
the hand-animated look where outlines shimmer. Use `stableRng` for anything that
must not move (layout of clouds, grass). Fonts are self-hosted via
`@fontsource/patrick-hand` (`HAND_FONT`) and `@fontsource/permanent-marker`
(`MARKER_FONT`); `main.ts` preloads them because canvas text doesn't always
trigger web-font loading. Ink colour is `INK` (matches the sprites'
`(20, 20, 26)`-ish lines).

The non-player art (enemy, pickups, toilet) is procedural for now; any of it can
be swapped for photographed drawings via the sprite pipeline below.

## Sound (`src/audio.ts`)

All sounds are synthesized live with WebAudio (a lowpassed sawtooth with a fast
amplitude "flutter" is the core fart). Any sound can be replaced by a real
recording: drop `src/assets/sfx/<name>.(mp3|ogg|wav|m4a)` and it's picked up by
`import.meta.glob` at build time — names are listed in
`src/assets/sfx/README.md`. `fly` is a loop driven every frame by
`setFlying(active, sputter)`; everything else is a one-shot `sfx(name)`. Audio
only starts after `unlockAudio()` runs inside a pointer event. Mute and best time
are persisted in `localStorage` (wrapped in try/catch).

## Sprite pipeline (hand-drawn art)

The user supplies new player poses as **photos of hand-drawn stick figures on
paper**. The recipe used throughout this project to turn one into a usable sprite:

1. `PIL.ImageOps.exif_transpose` to fix phone camera rotation.
2. Overlay a coordinate grid on a preview to find the figure's bounding box by
   eye.
3. Crop to that box with a little padding.
4. Grayscale → alpha-threshold to key out the white paper background (typical
   thresholds used so far: white ≈142, black ≈45 — tune per photo's lighting/
   contrast), keeping ink as solid color (`(20, 20, 26)` used so far) with
   anti-aliased edges.
5. Downscale to roughly 300–420px target width.
6. Save as RGBA PNG into `src/assets/player/`, add the import + `SpriteName`
   entry in `src/sprites.ts`.
7. Preview against a dark background (not just a bare checkerboard) before
   committing — thresholding artifacts are easy to miss otherwise.

## Verifying changes

There's no automated test suite. For anything that changes difficulty (level
layout, physics, economy), run `npm run sim -- check` — the same check CI runs
and blocks on — and re-`tune` (or run the Difficulty tune workflow) if a preset
drifts off target. Changes are verified by running the Vite dev
server and driving the page with **Playwright** (headless Chromium, already
available in this environment — see the top-level system docs on the pre-
installed browser): `page.mouse`/`page.touchscreen` to simulate input,
`window.__game` (dev server only) to set up states directly — e.g. teleport the
player next to the toilet or set `fartingPower` — instead of playing there,
`page.screenshot()` to capture state (for clicks, use `mouse.down()`, a ~100ms
wait, then `mouse.up()` like a real press: `page.mouse.click()` releases within
the same frame and once hid a bug that broke every on-canvas button for humans), occasionally CDP `Input.dispatchTouchEvent`
for multi-touch gestures. Prefer `devices['iPhone 12']` (or similar) contexts when
checking anything mobile/camera/viewport-related, as in the canvas-scaling fix.

**Lesson learned the hard way**: don't eyeball downscaled/thumbnail screenshots to
judge small movements — a real ~50px player shift was once misdiagnosed as "the
player isn't moving at all" purely from misjudging a thumbnail. When a visual diff
is subtle, either crop/zoom the screenshot before viewing it, or pixel-diff two
screenshots (`PIL.ImageChops.difference`) to confirm something actually changed
before chasing a phantom bug.
